## Context

Problem. A patient looking at free slots should see another patient's booking within seconds, and the admin dashboard should update without a manual refresh. Today the booking UI polls ([ADR-0009](0009-realtime-polling-now-sse-later.md)), and the Go SSE gateway of [ADR-0021](0021-go-realtime-gateway.md) was never built. The constraints are the same as before: total cost must stay at $0 on free tiers, no always-on resource ([ADR-0014](0014-hosting-region-and-cost.md)), no CDN caching of `/api` ([ADR-0023](0023-zero-cost-edge-front-door.md)), and the stream must carry no personal data. Correctness never depends on push: a stale slot that loses the race gets `409 SLOT_TAKEN` and a refetch.

The engineer decided on 2026-10-18 to use a managed pub/sub provider, and the Ably free package over plain SSE. The figures below were read on 2026-10-18 from the providers' official pages; anything not found on those pages is marked unverified.

## Decision

Ably, over plain SSE, for patients and admins. Server-side only keys; the browser holds a short-lived subscribe-only token. The design (decided 2026-10-18):

- **One-way, non-PII events.** The patient channel `slots:{doctor_id}:{date}` carries `slot_taken` and `slot_freed` with only `doctor_id`, `local_date`, `starts_at`, `kind` and `seq`. No appointment id, no patient data. The admin channel `admin:events` carries the dashboard events without personal data. A reschedule is a freed plus a taken.
- **Outbox relay.** A relay reads `appointment_events` after a commit-safe cursor and batch-publishes to Ably with the message id `<txid>.<id>`, advancing the cursor only after a 2xx response (at-least-once; the id deduplicates). It runs synchronously after each committing write, with a short timeout, before the response is sent.
- **Tokens.** Minted by `clinic-api` with the Ably key, through the Vercel proxy only: subscribe-only on one channel, five-minute TTL for patients; the admin token sits behind the admin role check ([ADR-0030](0030-staff-roles-and-access.md)).
- **Secret.** The Ably server key lives in a new Secret Manager secret `clinic-ably-api-key`, created by the engineer; agents never handle it. If it is unset the code runs with "push disabled, polling only", logged once.
- **Polling stays.** As the safety net: 60 s while push is healthy, 15 s with the existing backoff and idle stop while it is not ([ADR-0009](0009-realtime-polling-now-sse-later.md)). No CDN caching on `/api`.
- **Limits and how we bound them.** Connections and channels fail closed per Ably's limits page; the monthly message cap's behaviour is undocumented, so we bound it ourselves: a 25,000/month publish cap with fan-out <= 200 gives <= 5.0M < 6M, an 80% stats alarm, and no payment method on the account (engineer-verified 2026-10-18; evidence in [docs/evidence/ably-no-payment-method-2026-10-18.md](../evidence/ably-no-payment-method-2026-10-18.md); it was pending the engineer's check at Ably signup until then). What the page says, read from <https://ably.com/docs/platform/pricing/limits> on 2026-10-18: for connection and channel caps, usage in excess of the limit "will be restricted until existing resources are removed"; message and bandwidth limits "are enforced separately"; and "Ably will contact you to let you know that you need to upgrade your package". The page says nothing about rejecting messages at the monthly cap and nothing about a payment method, so neither is assumed.
- **Publish budget.** The API publishes at most 25,000 messages a month (a durable counter in the database). Each publish is delivered to at most 200 subscribers (the free connection limit), and Ably counts a publish plus each delivery, so 25,000 x (1 + 200) = 5,025,000, about 5.0M and below the 6M monthly allowance. This is the bound I own, because the provider documents nothing at the monthly cap. When the budget is spent the token endpoint answers `503 REALTIME_UNAVAILABLE` and the page polls.
- **What the service really does (observed against the live service in CI, first recorded in `contracts/events/README.md`, then corrected by the booking hook's tests in PR #44).** A JWT works as a raw `Authorization: Bearer <jwt>` value on the event-stream endpoint. A refused or expired token does not give an HTTP error status: the stream opens with `200` and its first frame is `event: error`, with code 40142 (token expired) or 40160 (the token may not read this channel). Codes 40140 to 40149 mean mint a new token; 40160 means do not retry and poll. The same message id was delivered once within the dedupe window, which is what makes the at-least-once relay safe; I got that last point from the CI run, and it is not written in the README on PR #39.
- **What was seen when the two cases differ.** An expired token gives an error frame (40142) on a 200 stream. A patient token that asks for `admin:events`, a channel it has no capability on, gets no error frame: the first chunk is a blank line, then silence. The README on PR #39 says 40160 for that case; the real service did not send it in the PR #44 run (head 1deffc3), so the hook treats silence as the refusal and the test proves it by the token's capability claim (one channel, subscribe only) plus no message arriving on the admin channel. The local stand-in in the PR #44 tests does send 40160; it is a stand-in for the third party only.
- **Live production check (observed by the gatekeeper, release 0cc0608).** One test booking and one cancel through `clinic.ericgitangu.com/api` took the 24 h message count of the production Ably app `clinical-booking-prod` from 17 to 21 (+4): a `slot_taken` and an admin event for the booking, a `slot_freed` and an admin event for the cancel. The same request with the same idempotency key replayed the stored result and published nothing more. The test patient is labelled as a test and its appointment is cancelled.
- **Acceptance, run in CI.** The scenarios (a) to (h) of the design passed in the `e2e-real` job 3110 (PR #44) against the real service: a booking by another visitor removes the slot from an open page within seconds without a poll, a cancel returns it after one refetch, a blocked push host falls back to polling, a rate-limited token endpoint shows `refused` and still converges by polling, a StrictMode double mount mints one token, an unchanged safety poll renders the grid zero times, and a patient token cannot read `admin:events`. (g), a re-delivered message applying once, runs only against a local stand-in (`apps/booking/e2e/support/fake-push.mjs`, started only with `E2E_PUSH_LOCAL=1`, never in CI), because the real service drops a repeated message id itself. The stand-in stands in for the third party only.
- **Production check of the page.** After release 748d7d8 the token endpoint answered 200 (no-store) for the site origin and 403 for a cross-site origin, and a real Chrome on a booking page went from `data-stream="polling"` with `data-polling="armed"` on load to `data-stream="live"` after one scroll and one key press: [docs/evidence/patient-live-push-production-2026-10-18.md](../evidence/patient-live-push-production-2026-10-18.md). That release's `ship-admin` failed for the missing `VERCEL_ADMIN_TOKEN`, so the later jobs have not yet run on a release.
- **Evidence.** The account is on the Free package with no payment method, and the keys, secret and CI contexts exist: [docs/evidence/ably-no-payment-method-2026-10-18.md](../evidence/ably-no-payment-method-2026-10-18.md).
- **Admin feed.** Descoped for this submission, see [ADR-0032](0032-admin-live-feed-descoped.md); the admin channel is defined but nothing subscribes to it.
- **Not needed:** WebSockets (SSE fits one-way slot events), a Go service, a read-only database role ([ADR-0015](0015-database-roles-and-migrations.md)) and stream tickets ([ADR-0022](0022-admin-auth-and-bot-protection.md)).

## Consequences

- Good: no always-on resource and no compute of ours on the push path; the free package asks for no card at signup (<https://ably.com/docs/platform/pricing/free>).
- Good: a failure of push degrades to polling, which already works.
- Bad (a new data processor): Ably sees slot events. They are non-PII by design (doctor, local date, start time, kind, sequence). README section 10 lists it.
- Bad (token in the URL), no longer applies: I expected to fall back to an `accessToken` query parameter if the header was unsupported. The live CI tests show `Authorization: Bearer` works, so the token stays out of URLs and logs. The mitigations (five-minute TTL, one subscribe-only channel, non-PII events) remain.
- Bad (relay-trigger debt): there is no always-on worker. An event that is blocked behind a concurrent open transaction waits for the next trigger (the next write or admin metrics request). The 60 s safety-net poll covers the UI. The real fix is a scheduled or always-on relay, which costs money or a platform we have avoided; not taken.
- Bad: messages are counted per delivery (N+1 per publish), so the monthly figure grows with viewers, not just with bookings. The cost check ([ADR-0016](0016-cicd-circleci-keyless-deploy.md)) is to read Ably's usage and warn at 50 percent of the free allowance. The free-tier proof stays pending measured usage.
- Bad: the cost ceiling rises from about $0.28 to about $0.34 a month for the extra secret ([ADR-0014](0014-hosting-region-and-cost.md)).

## Assessment line

Section 1 "components, key decisions, trade-offs": push for slot freshness without an always-on service.

## Review trigger

More than 150 peak concurrent connections, more than 3,000,000 messages in a month, or any change to Ably's free terms (limits, card requirement, enforcement at the limit): move to Cloudflare Durable Objects over WSS.

## Amendment (2026-10-19): the cursor holder drains; a relay that loses a race returns at once

The inline relay could return having sent nothing while a committed event was still unsent: another relay held the cursor row (`SKIP LOCKED` made the loser return at once, and the holder may have read its batch before the loser's event committed), so the event waited for the next trigger. The roles are now fixed.

- **A loser** (it finds the cursor row locked) returns immediately: no sleep, no retry. A booking never pays for another request's slow publish.
- **The holder** (it won the lock) drains. After each pass it takes a fresh snapshot and reads again, so events other writers committed while it was publishing are picked up. It stops when a pass finds nothing, after eight passes, or when too little of the relay's 2-second budget is left for another pass: a further pass starts only if the time left is at least 1.25 times the slowest pass so far (and at least 50 ms). A pass the budget would cancel mid-publish is never started, because a cancelled publish may already have been accepted over there with the cursor not moved, and the next trigger would send it again.
- **Failures.** A failed publish ends the drain. The messages that earlier passes of the same trigger sent are returned and are not undone (the cursor moved with them). The failure counts once toward the circuit breaker, even when an earlier pass succeeded. A failed pass keeps its budget debit (the answer may have been counted), and `debited_through` stops the next trigger from debiting it again.
- **Unchanged.** The `xmin` guard (nothing is published before its transaction is visible), the cursor moving only in the transaction that publishes (an event goes out once however many passes there are), the publish budget debited in that transaction (cap 25,000 a month), and the 60-second poll. The token mints (patient and admin) run the same relay, as holder or loser the same way. A mint whose request ends up holding the cursor waits for that drain, so it can take up to the 2-second relay budget before the token is returned; a loser's mint returns at once.

**What can still wait.** An event can still wait for a later trigger in four exact cases:

1. it commits after the holder's last read (the pass that finds nothing) and reaches the cursor lock before the holder commits that pass, so its own relay is a loser;
2. the holder stops at the eighth pass;
3. the holder stops at the deadline: with a push round trip of about 0.8 s or more the second pass does not fit (at 1.0 s the holder sends its own batch and returns at about 1 s);
4. an older transaction is still open, which keeps the event above the snapshot horizon until the trigger that follows that transaction's commit.

In each case the event is sent by the next booking's relay, or the next token mint (an open page asks for one on user input), or at the latest by the clients' 60-second poll; nothing is lost and nothing goes out twice.

**Cost.** The holder pays about twice the push round trip (0.85 s at 0.4 s and 1.25 s at 0.6 s with five concurrent bookers), bounded by the 2-second budget. Losers are back in a few tens of milliseconds: with five bookers over eight rounds (32 losers each) p50 was 19 ms and p95 37 ms at a 0.4 s round trip, p50 21 ms and p95 47 ms at 0.6 s. Race tests on real Postgres cover 2 and 5 bookers with round trips of 0.1, 0.4, 0.6 and 1.0 seconds (everything published once; at 1.0 s the remainder by the next mint), a loser under 50 ms, a stranded event flushed by a patient and by an admin token mint, a failure in a later pass, and the horizon guard; controls show the events left behind when the holder does not drain.
