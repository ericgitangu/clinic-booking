1 Scope and conventions

This document describes the Idyllic Clinic booking system as built on main at c59263e3, with production serving the v1.1.1 release (68449dd) until the next successful release. The assessment brief is the business need. Each requirement and constraint in it gets an identifier in section 3, and each identifier is traced to design, code, test and production behaviour in section 13.

Two numbered lists are used. D1 to D13 (section 4) are the answers to the brief's open questions, traced to their tests in 13.2. Decision 1 to Decision 35 are the design decision records on https://clinic.ericgitangu.com/decisions, each at its own anchor (#decision-3 for Decision 3); "Decision N" in this document means that record. Where a figure is an estimate rather than a measurement, it says so.

1.1 Naming

The product name is Idyllic Clinic, and the seeded clinic is named "Idyllic Clinic" (migration 0011). The repository and the Cloud Run services keep the neutral clinic-* names.

2 Business context

2.1 The scenario, as the brief states it

"We run a small clinic with 5 doctors. Patients need to book appointments online. Each doctor has set working hours and works in 30-minute slots. A patient should see which slots are free for a given doctor on a given day, pick one, and book it. Once booked, that slot must not be available to others. Patients should also be able to cancel. We're starting small but want to grow."Savannah Informatics, Backend Developer Take-Home Assessment, Section 1

The brief joins four sections into one scenario: design (1), build a REST API in FastAPI, Django REST Framework or Go (2), deploy with CI/CD that auto-deploys on merge (3), and a written reflection on the tools used (4). The time limit is three to five days. Its rules say "Clear reasoning matters as much as working code."

2.2 Stakeholders

2.3 Success criteria

  1. No double booking, ever, including under concurrent requests. This is the one property everything else depends on.
  2. The four required endpoints behave as the brief specifies, with meaningful errors and correct status codes, and the two bonus items work.
  3. A reviewer can verify the system independently: public URL, Swagger UI, a public CI project, copy-paste checks in the README.
  4. Merging to main deploys, and a pull request runs the tests.
  5. The design can grow from one clinic with 5 doctors without a rewrite of the booking core.
  6. Ambiguities are decided and written down, not left to the code to imply.
  7. Every deliverable the brief lists is present, including the Section 4 reflection (R16), which is README section 11.

I added one constraint of my own that the brief does not ask for: the running system should cost nothing. Section 11 states the one exception I accepted.

4.1 The one-hour rule

The brief's bonus says only "prevention of bookings within 1 hour of now". It says nothing about changes to an existing booking. Applying the rule to changes (D13) is my extension of the bonus, not brief text.

Decision
  • A new booking whose slot starts less than 60 minutes from now is 422 BOOKING_TOO_SOON.
  • A reschedule TARGET less than 60 minutes away is also 422 BOOKING_TOO_SOON: the new slot is validated as a fresh booking would be, which is exactly what R5 asks.
  • 409 CHANGE_TOO_LATE applies only when the CURRENT visit starts within the hour: cancelling it, or moving it away.
  • Exactly 60 minutes away is allowed. Availability never offers a slot starting within 60 minutes.
  • Staff (owner or admin) are exempt from the lead-time rule, both codes, and from nothing else. They still need a reason, which is audited, and stay bound by every other check (a start in the past, a visit that has begun, a taken slot, working hours, the 90-day horizon).

Why the split. The status rule in 7.3 decides it. A too-soon target is a property of the request: resending it unchanged can never succeed, so it is 422, and it keeps the reschedule validation identical to booking. A too-late change is a property of the appointment's current state, so it is 409.

Tests

backend/tests/integration/test_one_hour_rule.py drives each case: test_book_boundary, test_cancel_boundary, test_reschedule_boundary_on_the_current_start, test_reschedule_boundary_on_the_new_start, test_both_starts_under_an_hour_answers_409_the_current_start_is_checked_first, test_availability_never_offers_a_slot_inside_the_window, and for staff test_staff_are_exempt_from_the_rule_the_patient_is_held_to and test_staff_reschedule_is_exempt_from_both_codes. The availability filter keeps test_slots.py::test_lead_filter_excludes_near_slots.

In production: /openapi.json lists CHANGE_TOO_LATE, and its problem type document is served at /api/problems/change-too-late.

5.2 The admin side

  • Staff writes (Decision 33). Owner and admin book, move, cancel and veto for a patient through the same service functions the patient path uses. Each write needs a reason and writes an append-only staff_action_audit row in the same transaction. A veto undoes the patient's last change and locks the visit against further patient changes. Writes are throttled to 60 per person per 10 minutes.
  • Live feed (Decisions 9 and 21). The dashboard and appointment page stream from clinic-realtime through the admin app's /live/stream route, which signs the staff assertion. All tabs in one browser share one stream. Two streams can be open at once; a third viewer sees "Live feed busy" and the page refreshes every 30 seconds.
  • Live notifications. Each live event (a booking, a change, an arrival, a no-show, a veto) shows a toast to the staff who did not make it, an unread count on the live feed and a two-second highlight on the doctor's card. A burst becomes one "N updates" toast. It rides the existing stream and opens no new connection, and a viewer's toasts never carry a patient name.
  • Attendance (migration 0010). Staff mark a patient arrived, or a no-show once the visit has begun, in appointment_attendance. The runtime role may insert and select only, so a correction is a new row with an audited reason. The appointment's status does not change (6.4).
  • Doctor arrival email (migration 0017). Owner and admin may set an optional doctors.email on the doctor's card, an audited action (doctor_email). Marking a patient arrived writes one doctor_notification row in the same transaction; the admin app then claims it with a lease, takes one email from the shared allowance and records it sent, failed or skipped with a reason (no_email, allowance_day, allowance_month, demo_address, not_configured). Seeded doctors have no address, so nothing is emailed from seed data. The email names the patient by first name and last initial only. The address is shown to owner and admin, never to a viewer, and is in no public response.
  • Audit trail. The audit page reads every stored staff action back through /internal/admin/audit, doctor_email included; tests/integration/test_doctor_notice.py covers that read-back.

6 Data model and booking core

6.1 Entities

  • working_hours is a clinic-local window per doctor and ISO weekday; a CHECK pins both ends to :00 or :30. The seed gives each doctor their own weekly windows: Otieno 08:00 to 12:00 and 13:00 to 17:00 on weekdays; Kamau 09:00 to 17:00 on weekdays; Rotich 08:00 to 14:00 on Monday, Wednesday and Friday; Mwangi 10:00 to 18:00 on Tuesday and Thursday and 09:00 to 13:00 on Saturday; Njeri 07:00 to 11:00 Monday to Saturday.
  • appointments carries CHECKs for the status set, ends_at = starts_at + 30 min, the half-hour grid, and cancel consistency (a cancelled row has a reason and a time; a booked row has neither).
  • appointment_events is written in the same transaction as every change. It is the event history, the admin lineage view, the outbox and the source the Go service streams. Its txid xid8 column gives a commit-safe cursor.
  • appointment_attendance (0010) holds staff marks, arrived or no_show; the latest row is the current mark. staff_action_audit (0009) holds every staff write with its actor, action and reason, and leaves patient name, phone and email out on purpose. doctor_notification (0017) records each arrival email, one per appointment and kind. doctors.email (0017) is nullable and normalised by a CHECK.
  • Migrations are hand-written and expand-only, linted in CI. clinic_app has SELECT, INSERT and UPDATE, no DELETE, and cannot rewrite alembic_version; on the attendance table it has INSERT and SELECT only.

6.2 Slot computation

Slots are computed, never stored (Decision 4). Each availability request makes two indexed queries: the doctor's working hours, and the booked starts over the UTC range [D 00:00, D+1 00:00) of the clinic-local day. domain/slots.py then cuts each working window into 30-minute steps in UTC, de-duplicates by local wall time, subtracts the booked starts, and drops anything before now + 60 min (R3, R8). The slot function itself does no I/O; the pure domain package, which includes it, is held to 95% coverage by unit tests alone. Availability answers with an ETag and honours If-None-Match with a 304.

What I gave up: there is no slot row to lock, so uniqueness cannot live on the slot. It lives on the appointment, which is the next section.

6.3 The concurrency guarantee

Check-then-insert fails under concurrency, and SELECT ... FOR UPDATE cannot lock a row that does not exist yet. So the database decides:

CREATE UNIQUE INDEX uq_appt_doctor_slot_booked
  ON appointments (doctor_id, starts_at) WHERE status = 'booked';
CREATE UNIQUE INDEX uq_appt_patient_slot_booked
  ON appointments (patient_id, starts_at) WHERE status = 'booked';

The service validates the request, inserts, and maps the unique violation (SQLSTATE 23505, by constraint name) to 409 SLOT_TAKEN or 409 PATIENT_DOUBLE_BOOKED. There is deliberately no "is it free?" pre-check: it would be a window for a race and adds nothing the index does not enforce. A cancelled row leaves the partial index, so the slot is bookable again (R4) while the history stays.

How the test proves it, and why it cannot pass vacuously

tests/concurrency/test_race_same_slot.py releases 25 concurrent POSTs for one slot at an asyncio.Barrier, holds each transaction open with a test-only pg_sleep(0.2), and samples pg_locks every 20 ms. It repeats over 10 slots (pool size 30, so all 25 are in flight). Per slot it asserts exactly one 201, 24 409s with SLOT_TAKEN and one booked row. Across the run it asserts a peak of at least 5 transactions waiting on another transaction's lock at once, so the test fails if it ever stops being concurrent.

The naive control (test_naive_control.py) is a raw check-then-insert (asyncpg, with pg_sleep(0.1) between the check and the insert), released at its own barrier against a separate database migrated the same way, with the doctor-slot index dropped. It asserts more than one booked row. That is what shows the index, not luck, is what holds.

A reschedule takes the row with SELECT ... FOR UPDATE and updates starts_at in place. If the new slot is taken the transaction rolls back and the original booking is untouched. A deadlock or serialization failure is retried once with jitter, then reported as 409 CONCURRENT_UPDATE.

6.4 Appointment state machine and attendance

Guards on every change, in order: the appointment exists (else 404), is not cancelled (409 APPOINTMENT_ALREADY_CANCELLED), has not started (409 APPOINTMENT_ALREADY_STARTED). For a reschedule, a request for the start it already has then returns the appointment unchanged (D7); otherwise the doctor must still be active (else 422 UNKNOWN_DOCTOR) and the new slot passes the same validator as a booking. The one-hour guard on the current visit (409 CHANGE_TOO_LATE) runs before the new slot is checked, for patients (4.1). A visit locked by a staff veto refuses further patient changes (APPOINTMENT_LOCKED).

Attendance is a staff record, not a state. arrived and no_show live in appointment_attendance, written only by staff, inside the window the API allows (else ATTENDANCE_WINDOW_CLOSED), and never on a cancelled appointment. The status stays booked, so the partial unique index, the availability query and the patient's view are unaffected by attendance.

6.5 Time model

  • Storage is UTC timestamptz. The clinic zone is data; production returns "timezone": "Africa/Nairobi" on the clinic.
  • Input must be RFC 3339 with an offset (D3). Output is in the clinic offset plus a timezone field.
  • The clock is injected through a FastAPI dependency. Business SQL never calls now(). Ruff bans datetime.now, utcnow and today outside core/clock.py, so tests pin time and pass on any weekday.
  • Nairobi has no daylight saving, so the DST tests run in Europe/Berlin. Slot stepping in UTC skips the spring-forward gap and de-duplicates the fall-back hour.

7.2 Idempotency keys

Idempotency-Key (1 to 255 visible ASCII characters) is read on POST /appointments and scoped to the patient. The key and a fingerprint of doctor and time are stored on the appointment under a partial unique index. The same key with the same doctor and time replays the original 201 with Idempotent-Replayed: true, answered before validation, so a retry after the slot has passed still gets its booking. The same key with a different doctor or time is 422 IDEMPOTENCY_KEY_REUSED; a key whose appointment has left booked is 409 IDEMPOTENCY_KEY_CONSUMED. On any unique violation the key is re-checked before answering, because a lost response must never read as "your slot was taken" (Decision 13).

7.3 Error model: RFC 9457

Every non-2xx is application/problem+json with type, title, status, detail, a stable machine code and a request_id that also appears in the logs. The catalogue is closed: 40 codes in the ProblemCode enum, and a unit test checks the domain errors, the handlers, the enum and contracts/api-errors.md against one list (Decision 6).

The status rule

404: the resource in the path does not exist. 422: the request is well-formed but resending it unchanged can never succeed. 409: it conflicts with current state and might succeed later or in another state.

Main booking codes. The full list of 40, including validation, auth, staff, rate-limit and push codes, is in contracts/api-errors.md.

10 Deployment and CI/CD

The main branch deploys. Pull requests run the verify jobs only. A push to main runs the same jobs (without the PR-only dast) and then ships. The workload identity federation condition in Terraform admits only refs/heads/main in this repository and a job that uses the deploy context, so editing the config on a branch cannot deploy. The deploy contexts are also restricted to main in CircleCI's project settings.

The CircleCI project is public, so every run can be inspected: app.circleci.com/pipelines/github/ericgitangu/clinic-booking. The API is readable without a login too: GET circleci.com/api/v2/project/gh/ericgitangu/clinic-booking/pipeline?branch=main returns the pipelines and their job logs.

How long it takes. A pull request pipeline takes about 18 minutes and a release 28 to 29, set by the slowest jobs (e2e-real about 18 minutes, admin-e2e 11 to 13, backend-test 8 to 10). Every suite runs to the end and the job still fails if anything failed, so one red test does not hide the others. go-quality retries module downloads with a bounded backoff and caches them, with checksum verification left on.

10.2 Smoke check and rollback

A release is a tagged, no-traffic Cloud Run revision that has to pass the claims check before it gets traffic. Going back is a traffic move, not a rebuild. Rollback refuses to move to the placeholder image, and refuses when something else has already moved traffic. .circleci/rollback.yml is the one-click version, and the rollback runbook is on the decisions page (#rollback). The image prune keeps the serving image and the rollback image and deletes everything else; a newer image is kept as in flight only when its tag is the current head of main.

Current release

Production runs v1.1.1, which is main at 68449dd. clinic-api and clinic-realtime both send 100% of traffic to the revision tagged sha-68449dd and keep the sha-e82c278 revision as the rollback target. Artifact Registry holds two images per service: the serving one and the rollback one.

11 Operations, cost and security

11.1 Cost: the $0 posture and its one exception

Every running part sits inside a published free tier: Cloud Run compute and egress in a Tier 1 region, Neon Free, Vercel Hobby, Ably's free package (no payment method on the account), Resend's free limits enforced in the database, and CircleCI's free credits. cost_check.sh runs statically on every PR and live after each API deploy, and has a self-test that mutates the config to prove it fails.

The one exception: shared billing

The GCP project shares a billing account with other projects whose use has already exhausted the shared Artifact Registry and Secret Manager free tiers. This project's share is estimated at about $0.41 a month against a ceiling of $0.50 a month: six enabled secret versions at $0.06 are $0.36, plus about $0.05 of registry storage. Check C5 in cost_check.sh computes the share from the live secret count and fails if the ceiling is exceeded or the count cannot be read. Cloud Run compute and egress stay inside the free tier. A $1 alert budget (infra/billing/budget.tf) and a $3 Cloud Run spend cap (console-managed) stand behind it.

11.3 Abuse controls

  • Per-client rate limit in the Vercel proxy: 120 requests a minute by default, per instance. There is no general request rate limit inside the API, where no trustworthy client IP exists behind the proxy; the push-token endpoint has its own per-address limits (below).
  • reCAPTCHA Enterprise assessment on each book, cancel and reschedule in the web app.
  • Push tokens are rate-limited per address per minute (in memory) and per day (in the database), answering 429 RATE_LIMITED; a monthly publish budget turns push off (503 REALTIME_UNAVAILABLE) and the page polls.
  • Email day and month limits are reserved atomically before a send, so a burst cannot run past Resend's free tier, and 20 a day stay reserved for booking acknowledgements.
  • Staff writes are throttled to 60 per person per 10 minutes; one live stream per person and two in all.
  • A kill switch (scripts/ops/kill_switch.sh) and a production ZAP baseline.

11.4 Observability

Structured logs with a request id on every line and in every problem body, no PII. A Cloud Monitoring egress alert policy exists and is one of the live cost guards. Deploys are recorded as CircleCI deploy markers.
